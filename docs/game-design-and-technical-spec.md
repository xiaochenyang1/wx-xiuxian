# 《我的修仙日记》游戏设计与技术规范

## 1. 当前版本定位

当前版本为纯前端、单机、本地存档的竖屏修仙放置小游戏。

本阶段目标：

1. 保证核心修炼循环无需网络即可完整运行。
2. 保证浏览器预览和微信小游戏使用同一套数值与存档逻辑。
3. 保证关闭、切后台和重新打开后，进度可以稳定恢复并结算离线收益。
4. 保留未来接入账号、云存档和权威服务端的清晰边界。

本阶段明确不包含：

- 登录、Token、会话和账号系统
- HTTP、WebSocket 或其他业务 API
- PostgreSQL、Redis、消息队列和容器服务
- 云存档、跨设备同步、服务端防作弊
- 真实排行榜、支付、广告和运营后台

## 2. 核心循环

```text
自动修炼
  -> 获得修为与灵石
  -> 自动升级或到达境界瓶颈
  -> 消耗突破丹完成突破
  -> 提升基础战力和挂机效率
  -> 获得材料、功法和法宝
  -> 调整装备组合
  -> 继续自动修炼
```

### 2.1 修炼

- 在线效率：100%。
- 离线效率：70%。
- 单次离线结算上限：24 小时。
- 修为、灵石和掉落时钟均保存余数，减少频繁结算造成的累计误差。
- UI 每秒显示投影值，实际快照在检查点或玩法写操作时结算。
- 前台自动检查点间隔：30 秒。

### 2.2 升级与突破

- 普通等级修为填满后自动升级。
- 境界最高等级修为填满后进入 `breakthrough_ready`。
- 突破消耗当前境界配置中的突破丹数量。
- Lv.1000 进入 `version_cap`，后续修为转入修为储备。
- 等级、境界、战力、每秒修为和每分钟灵石都从同一快照派生。

### 2.3 新手任务

| 条件 | 状态 | 奖励 |
|---|---|---|
| 达到 Lv.3 | 自动完成 | 无额外奖励 |
| 达到 Lv.5 | 自动完成 | 无额外奖励 |
| 达到 Lv.8 | 自动完成并领取 | 突破丹 x1 |

任务完成时间、领取时间和奖励与角色快照一起落盘。Lv.8 奖励只能在任务从未完成变为完成时发放一次。

### 2.4 掉落与收获箱

每 60 秒有效挂机时间产生一次掉落尝试。当前掉落池包括：

- 木材、石材、灵土、灵草、矿石
- 强化石
- 突破丹
- 普通或优秀法宝
- 普通或优秀功法

材料直接进入背包堆叠。法宝和未处理功法进入最多 100 格的收获箱。普通和优秀品质可按设置自动分解；收获箱已满时，新候选会自动分解，防止存档无限增长。

### 2.5 背包

- 初始容量：50 格。
- 每次扩容：10 格。
- 最大容量：200 格。
- 第 `n` 次扩容费用：`5000 * n^2` 灵石。
- 堆叠物品占 1 格，已收入行囊或已装备的法宝各占 1 格。

### 2.6 功法与法宝

功法槽：心法、身法、神通、秘术。

法宝槽：武器、防具、饰品左、饰品右、坐骑、灵宠。

装备变化后统一重算：

- 固定战力
- 每秒修为加成
- 每分钟灵石加成
- 掉落效率加成

所有装备操作直接写入本地快照，不存在待同步队列或网络冲突状态。

## 3. 本地存档设计

### 3.1 存储位置

| 平台 | 实现 | 键 |
|---|---|---|
| 浏览器 | `localStorage` | `cultivation-diary.local-save.v1` |
| 微信小游戏 | `wx.getStorageSync/setStorageSync` | `cultivation-diary.local-save.v1` |

### 3.2 存档信封

```ts
interface LocalGameSave {
  schemaVersion: 1;
  savedAt: string;
  spiritStoneRemainderMicros: number;
  dropClockRemainderMicros: number;
  snapshot: BootstrapSnapshot;
}
```

`BootstrapSnapshot` 包含角色、修炼、货币、背包、功法、法宝、收获箱、任务、解锁、设置和待展示的离线汇总。

### 3.3 写入时机

1. 新档创建后立即写入。
2. 每次突破、改名、使用物品、收取、分解、装备或设置变化后写入。
3. 前台每 30 秒写入。
4. 切后台时写入。
5. 回到前台完成离线结算后写入。
6. 关闭离线收益弹窗后写入。

玩法写操作遵循“先结算、再修改、最后整体写入”的顺序，避免装备效率变化被错误应用到之前的挂机时间。

### 3.4 读取与损坏处理

本地存储是不可信输入。载入前至少检查：

- schema 版本与时间戳
- 等级、余数、背包容量和集合长度边界
- 非负十进制字符串
- 角色形象、修炼状态和关键布尔设置
- 收获箱最大长度

校验失败时不把旧数据渲染到 UI，而是创建新档。未来 schema 升级应先增加显式迁移函数；不能静默猜测旧字段含义。

### 3.5 写入失败

浏览器隐私模式、微信存储配额或平台异常可能导致落盘失败。此时：

- 当前会话继续运行。
- `storageStatus` 切换为 `volatile`。
- 顶部显示“本地存档不可用，本次进度仅保留到退出游戏”。
- 后续检查点继续尝试写入，成功后恢复为 `saved`。

## 4. 生命周期结算

### 4.1 前台

`AppView` 以最近快照为锚点逐秒投影修为。投影只改变显示，不直接改存档。

自动检查点或玩法操作触发时，`LocalGameService` 使用 100% 效率把锚点结算到当前时间，更新真实快照并重新建立 UI 投影锚点。

### 4.2 后台

收到隐藏事件时：

1. 以 100% 效率结算到隐藏时刻。
2. 写入完整快照。
3. UI 停止继续推进投影。

### 4.3 返回前台

收到显示事件时：

1. 计算上次结算时间到当前时间的差值。
2. 截断到 24 小时。
3. 以 70% 效率统一结算修为、灵石和掉落时钟。
4. 同步任务和解锁状态。
5. 生成离线收益汇总并落盘。
6. 先展示收益弹窗，再继续排队的升级表现。

不足 60 秒的后台时间仍会结算，但不弹出离线收益汇总，避免短暂切屏反复打断玩家。

## 5. 前端模块边界

```text
GameBootstrap
  -> LocalGameService
       -> shared 数值与领域函数
       -> PlatformAdapter 本地存储
  -> AppStore
  -> AppView
```

### `GameBootstrap`

- 绑定 Cocos 生命周期。
- 串行化本地玩法操作。
- 触发自动检查点。
- 把新快照交给 Store 和表现队列。

### `LocalGameService`

- 是当前版本唯一的游戏状态写入入口。
- 负责存档校验、结算、掉落、任务、背包和装备操作。
- 不依赖 HTTP、账号或平台登录。

### `PlatformAdapter`

- 只提供本地存储、前后台事件、安全区和轻触反馈。
- 浏览器与微信实现保持同一接口。

### `shared`

- 是浏览器侧构建依赖，不是服务端包。
- 提供境界、资产配置、经验曲线、经济结算、战力和装备加成纯函数。

### `AppStore` 与 `AppView`

- Store 保存当前可渲染状态、页面和本地存储状态。
- View 只读取快照并发送用户意图，不直接写存档。

## 6. 开发调试

仅 `DEBUG` 构建显示调试面板，可执行：

- 修满当前等级
- 增加 10000 灵石
- 增加 1 枚突破丹
- 模拟离线 1、8、24 小时
- 使用随机或固定 32 位无符号掉落种子
- 二次确认后重置本地存档

Release 构建不创建调试根节点。调试能力仍走 `LocalGameService` 的正常存档路径，避免形成另一套状态模型。

## 7. 验收基线

### 静态验收

- `pnpm typecheck` 通过（含 `test/` 的独立 TypeScript 程序）。
- `pnpm test` 通过。
- `pnpm verify:release-config` 通过。
- 仓库中不存在 `server/`、数据库迁移和 Docker 配置。
- 客户端源码中不存在 `fetch`、`wx.request`、API base URL、Token 或重连队列。

### 浏览器验收

- 新档可进入主页并持续增长修为。
- 刷新页面后角色、背包和装备保持一致。
- 后台超过 60 秒再返回时出现离线收益汇总。
- 突破、改名、扩包、物品使用、收取、分解和装备后刷新不回退。
- 本地存储不可用时出现明确提示，当前会话仍能操作。
- 重置进度需要二次确认，完成后回到全新 Lv.1 角色。

### 微信验收

- 刘海屏、圆角屏和胶囊按钮区域无遮挡。
- 切前后台只结算一次，不重复发放收益。
- 杀进程后重新进入可以恢复存档。
- 存储配额和写入失败提示符合预期。
- Release 包不包含开发调试面板。

## 8. 未来重新引入后端

需要云存档、跨设备同步、排行榜、防作弊或商业化时再增加后端。推荐顺序：

1. 保持 `shared` 领域规则为唯一数值来源。
2. 为 `LocalGameService` 抽象一个 `GamePersistence` 接口。
3. 先实现可选云备份，不立即把所有操作改成网络强依赖。
4. 明确冲突策略、账号迁移、存档版本和失败回滚。
5. 排行榜、支付和可交易资产必须改为服务端权威。
6. 在现有本地测试基线之上补充集成和端到端测试，不复用本阶段已删除的旧服务端测试。

在这些需求出现之前，当前版本应保持无网络依赖，避免为了可能的未来需求重新引入空置服务端。
