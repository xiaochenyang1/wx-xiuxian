# 《我的修仙日记》游戏设计与技术规范

## 1. 当前版本定位

当前版本为纯前端、单机、本地存档的竖屏修仙放置小游戏。

本阶段目标：

1. 保证核心修炼循环无需网络即可完整运行。
2. 保证浏览器预览和微信小游戏使用同一套数值与存档逻辑。
3. 保证关闭、切后台和重新打开后，进度可以稳定恢复并结算离线收益。
4. 保留未来接入账号、云存档和权威服务端的清晰边界。

本阶段明确不包含：

- 登录、Token、会话和账号系统
- HTTP、WebSocket 或其他业务 API
- PostgreSQL、Redis、消息队列和容器服务
- 云存档、跨设备同步、服务端防作弊
- 真实排行榜、支付、广告和运营后台

## 2. 核心循环

```text
自动修炼
  -> 获得修为与灵石
  -> 自动升级或到达境界瓶颈
  -> 消耗突破丹完成突破
  -> 提升基础战力和挂机效率
  -> 获得材料、功法和法宝
  -> 炼丹、炼器并培养道侣与宗门声望
  -> 强化法宝、升星功法并调整装备组合
  -> 挑战历练并领取首通资源
  -> 继续自动修炼
```

### 2.1 修炼

- 在线效率：100%。
- 离线效率：70%。
- 单次离线结算上限：24 小时。
- 修为、灵石和掉落时钟均保存余数，减少频繁结算造成的累计误差。
- UI 每秒显示投影值，实际快照在检查点或玩法写操作时结算。
- 前台自动检查点间隔：30 秒。

### 2.2 升级与突破

- 普通等级修为填满后自动升级。
- 境界最高等级修为填满后进入 `breakthrough_ready`。
- 突破消耗当前境界配置中的突破丹数量。
- Lv.1000 进入 `version_cap`，后续修为转入修为储备。
- 等级、境界、战力、每秒修为和每分钟灵石都从同一快照派生。

### 2.3 新手任务

| 条件 | 状态 | 奖励 |
|---|---|---|
| 达到 Lv.3 | 自动完成 | 无额外奖励 |
| 达到 Lv.5 | 自动完成 | 无额外奖励 |
| 达到 Lv.8 | 自动完成并领取 | 突破丹 x1 |

任务完成时间、领取时间和奖励与角色快照一起落盘。Lv.8 奖励只能在任务从未完成变为完成时发放一次。

### 2.4 掉落与收获箱

每 60 秒有效挂机时间产生一次掉落尝试。当前掉落池包括：

- 木材、石材、灵土、灵草、矿石
- 强化石
- 突破丹
- 普通或优秀法宝
- 普通或优秀功法

材料直接进入背包堆叠。法宝和未处理功法进入最多 100 格的收获箱。普通和优秀品质可按设置自动分解；收获箱已满时，新候选会自动分解，防止存档无限增长。

### 2.5 背包

- 初始容量：50 格。
- 每次扩容：10 格。
- 最大容量：200 格。
- 第 `n` 次扩容费用：`5000 * n^2` 灵石。
- 堆叠物品占 1 格，已收入行囊或已装备的法宝各占 1 格。

### 2.6 功法与法宝

功法槽：心法、身法、神通、秘术。

法宝槽：武器、防具、饰品左、饰品右、坐骑、灵宠。

装备变化后统一重算：

- 固定战力
- 每秒修为加成
- 每分钟灵石加成
- 掉落效率加成

所有装备操作直接写入本地快照，不存在待同步队列或网络冲突状态。

法宝强化为必定成功，行囊和已装备法宝均可强化，收获箱中的法宝不可操作。目标强化等级 `n = 当前等级 + 1`，上限为 `+20`：

- 强化石：`ceil(ceil(n / 2) * 品质倍率)`
- 灵石：`ceil(250 * n * 品质倍率)`
- 品质倍率依次为普通 `1.0`、优秀 `1.5`、稀有 `2.5`、史诗 `4.0`、传说 `7.0`、神话 `12.0`、洪荒 `20.0`

强化每级使法宝基础战力增加 `10%`，不放大词条。资源不足时不扣除任何内容，按钮仍可点击以显示精确缺口。

重复收取已拥有功法时增加 `duplicateCount`。功法升星必定成功，不消耗灵石或功法残页，目标星级 `2..10` 对应的同名副本消耗为 `1、1、2、2、3、4、5、7、10`。星级与品质共同放大功法战力和挂机加成。

`refreshSnapshot` 会根据配置、品质、星级和强化等级重新生成每件资产的派生字段，再从已装备资产汇总角色战力与效率；存档中的旧派生展示值不会被当作权威数值。

### 2.7 洞府

Lv.11 解锁。洞府内有五座建筑，每座 `0` 到 `10` 级，`0` 表示未建造。

| 建筑 | 加成维度 | 每级加成 |
|---|---|---|
| 聚灵阵 | 每秒修为 | +3% |
| 灵田 | 每分钟灵石 | +4% |
| 炼丹房 | 掉落效率 | +2.5% |
| 闭关室 | 每秒修为 | +1.5% |
| 炼器室 | 固定战力 | +50 |

升到第 `n` 级的造价：

- 灵石：`3000 * n^2`
- 材料：每种 `5 * n`，取自挂机掉落的木材、石材、灵土、灵草和矿石

洞府加成与功法法宝加成走同一条管线：`calculateCaveBonuses` 算出的 `LoadoutBonuses` 与装备加成在 `refreshSnapshot` 中求和后写入 `progress`，`settleCultivation` 不感知洞府的存在。

升级校验顺序为解锁、满级、灵石、材料，任何一项不满足都不扣除资源。资源不足时按钮仍可点击，点击后给出缺口数量。

### 2.8 历练

历练是六关顺序推进的一次性关卡：没有体力、计时、随机战斗、重复刷取或失败惩罚。只能挑战当前进度的下一关，角色当前总战力达到门槛后立即完成并领取首通奖励。

| 关卡 | 战力门槛 | 灵石 | 物资 |
|---|---:|---:|---|
| 青石山道 | 100 | 300 | 木材 x5、石材 x5 |
| 雾隐林 | 400 | 700 | 灵土 x5、灵草 x5 |
| 黑水泽 | 800 | 1,500 | 矿石 x10、强化石 x2 |
| 剑痕谷 | 1,200 | 3,000 | 木材 x10、石材 x10、矿石 x10 |
| 赤砂矿窟 | 3,500 | 6,000 | 灵土 x15、灵草 x15、强化石 x5 |
| 古修遗府 | 6,500 | 12,000 | 五类洞府材料各 x20、强化石 x8 |

存档只记录按配置顺序排列的 `clearedStageIds` 前缀。通关与领奖是同一事务；发奖前预检新增背包栈位，空间不足时不增加灵石、物资或通关进度。首通后的关卡不能重复领取奖励。

### 2.9 炼丹与炼器

炼丹按固定配方消耗材料和灵石，产物直接进入行囊：

| 配方 | 洞府要求 | 灵石 | 材料 | 产物 |
|---|---:|---:|---|---|
| 小经验丹 | 炼丹房 Lv.0 | 300 | 灵草 x4、灵土 x2 | 小经验丹 x1 |
| 大经验丹 | 炼丹房 Lv.2 | 1,500 | 灵草 x12、灵土 x8 | 大经验丹 x1 |
| 双修丹 | 炼丹房 Lv.3 | 2,000 | 灵草 x15、灵土 x10 | 双修丹 x1 |
| 突破丹 | 炼丹房 Lv.4 | 3,000 | 灵草 x20、矿石 x5 | 突破丹 x1 |

小经验丹模拟 1 小时在线修为，大经验丹模拟 6 小时在线修为。炼制前同时校验洞府等级、灵石、材料和新增栈位；失败不扣除资源。

炼器支持武器、防具、饰品、坐骑和灵宠五类定向打造，依次要求炼器室 `Lv.0..4`。基础品质权重为普通 `7000`、优秀 `2200`、稀有 `650`、史诗 `140`、传说 `10`；炼器室等级会降低普通权重并提高更高品质权重。优秀及以上产物按品质生成一至三个修为、灵石或掉落词条。打造前预检材料、灵石和行囊法宝空位，产物生成与扣费在同一本地事务中完成。

### 2.10 伴侣与宗门

Lv.11 解锁伴侣。玩家从君如兰、苏晚晴、陆星河中选择一位且不可更换，分别提供修为、灵石或掉落加成。结缘后为 Lv.1，消耗双修丹获得 100 亲密；升到目标等级 `n` 需要 `100 * n` 亲密，最高 Lv.10。加成随等级线性增长并通过 `calculatePartnerBonuses` 汇入统一挂机管线。

Lv.11 后可从青云宗、丹霞谷、万象楼中选择一个本地宗门且不可改投，分别提供修为、灵石或掉落加成。每次捐献消耗木材、石材、灵草各 5 个并增加 100 贡献；升到目标等级 `n` 需要 `100 * n²` 贡献，最高 Lv.10。宗门加成通过 `calculateSectBonuses` 汇入统一挂机管线。

### 2.11 本地试炼排行

排行不是在线服务。战力、等级、财富、洞府和伴侣五个榜单都把玩家当前真实存档与五名固定 NPC 标杆一起排序，明确标记为“本地试炼榜”。该功能不发送网络请求，也不声称展示其他真实玩家。

## 3. 本地存档设计

### 3.1 存储位置

| 平台 | 实现 | 键 |
|---|---|---|
| 浏览器 | `localStorage` | `cultivation-diary.local-save.v1` |
| 微信小游戏 | `wx.getStorageSync/setStorageSync` | `cultivation-diary.local-save.v1` |

### 3.2 存档信封

```ts
interface LocalGameSave {
  schemaVersion: 1;
  savedAt: string;
  spiritStoneRemainderMicros: number;
  dropClockRemainderMicros: number;
  snapshot: BootstrapSnapshot;
}
```

`BootstrapSnapshot` 包含角色、修炼、货币、背包、功法、法宝、收获箱、洞府、历练、伴侣、宗门、任务、解锁、设置和待展示的离线汇总。

配置版本记录在 `snapshot.config.version`，当前为 `local-2.0.0`；`schemaVersion` 仍为 `1`。

### 3.3 写入时机

1. 新档创建后立即写入。
2. 每次突破、改名、使用物品、收取、分解、装备、资产养成、洞府升级、炼丹、炼器、伴侣培养、宗门捐献、历练通关或设置变化后写入。
3. 前台每 30 秒写入。
4. 切后台时写入。
5. 回到前台完成离线结算后写入。
6. 关闭离线收益弹窗后写入。

玩法写操作遵循“先结算、再修改、最后整体写入”的顺序，避免装备效率变化被错误应用到之前的挂机时间。

### 3.4 读取与损坏处理

本地存储是不可信输入。载入前至少检查：

- schema 版本与时间戳
- 等级、余数、背包容量和集合长度边界
- 非负十进制字符串；余额与数量必须是整数，`experiencePerSecond` 和 `spiritStonePerMinute` 是仅有的两个允许带小数的投影值
- 角色形象、修炼状态和关键布尔设置
- 收获箱最大长度
- 洞府建筑 id 合法、无重复、数量与配置一致，等级为 `0..10` 的整数
- 历练通关 id 必须恰好是当前六关配置的一个前缀，不能未知、重复、跳关或乱序
- 伴侣与宗门 id 必须来自配置，未选择时等级和进度必须为 0，已选择时等级与当前升级进度必须在合法范围内

校验失败时不把旧数据渲染到 UI，而是创建新档。未来 schema 升级应先增加显式迁移函数；不能静默猜测旧字段含义。

### 3.4.1 已有迁移

迁移按版本逐步执行：

1. `local-1.0.0 → local-1.1.0`：为旧档补入五座 `0` 级洞府建筑。
2. `local-1.1.0 → local-1.2.0`：补入空的 `expedition.clearedStageIds`。
3. `local-1.2.0 → local-2.0.0`：补入未选择的伴侣与未加入的宗门记录。

因此 `local-1.0.0` 可以在一次载入中连续迁移到当前版本。迁移不改动其他字段，也不发放补偿资源；版本号不在这条明确迁移链上的存档仍按损坏处理。

### 3.5 写入失败

浏览器隐私模式、微信存储配额或平台异常可能导致落盘失败。此时：

- 当前会话继续运行。
- `storageStatus` 切换为 `volatile`。
- 顶部显示“本地存档不可用，本次进度仅保留到退出游戏”。
- 后续检查点继续尝试写入，成功后恢复为 `saved`。

## 4. 生命周期结算

### 4.1 前台

`AppView` 以最近快照为锚点逐秒投影修为。投影只改变显示，不直接改存档。

自动检查点或玩法操作触发时，`LocalGameService` 使用 100% 效率把锚点结算到当前时间，更新真实快照并重新建立 UI 投影锚点。

### 4.2 后台

收到隐藏事件时：

1. 以 100% 效率结算到隐藏时刻。
2. 写入完整快照。
3. UI 停止继续推进投影。

### 4.3 返回前台

收到显示事件时：

1. 计算上次结算时间到当前时间的差值。
2. 截断到 24 小时。
3. 以 70% 效率统一结算修为、灵石和掉落时钟。
4. 同步任务和解锁状态。
5. 生成离线收益汇总并落盘。
6. 先展示收益弹窗，再继续排队的升级表现。

不足 60 秒的后台时间仍会结算，但不弹出离线收益汇总，避免短暂切屏反复打断玩家。

## 5. 前端模块边界

```text
GameBootstrap
  -> LocalGameService
       -> shared 数值与领域函数
       -> PlatformAdapter 本地存储
  -> AppStore
  -> AppView
```

### `GameBootstrap`

- 绑定 Cocos 生命周期。
- 串行化本地玩法操作。
- 触发自动检查点。
- 把新快照交给 Store 和表现队列。

### `LocalGameService`

- 是当前版本唯一的游戏状态写入入口。
- 负责存档校验、结算、掉落、任务、背包、资产养成、洞府和历练操作。
- 不依赖 HTTP、账号或平台登录。

### `PlatformAdapter`

- 只提供本地存储、前后台事件、安全区和轻触反馈。
- 浏览器与微信实现保持同一接口。

### `shared`

- 是浏览器侧构建依赖，不是服务端包。
- 提供境界、资产配置、经验曲线、经济结算、战力和装备加成纯函数。

### `AppStore` 与 `AppView`

- Store 保存当前可渲染状态、页面和本地存储状态。
- View 只读取快照并发送用户意图，不直接写存档。

## 6. 开发调试

仅 `DEBUG` 构建显示调试面板，可执行：

- 修满当前等级
- 增加 10000 灵石
- 增加 1 枚突破丹
- 模拟离线 1、8、24 小时
- 使用随机或固定 32 位无符号掉落种子
- 二次确认后重置本地存档

Release 构建不创建调试根节点。调试能力仍走 `LocalGameService` 的正常存档路径，避免形成另一套状态模型。

## 7. 验收基线

### 静态验收

- `pnpm typecheck` 通过（含 `test/` 的独立 TypeScript 程序）。
- `pnpm test` 通过。
- `pnpm verify:release-config` 通过。
- 仓库中不存在 `server/`、数据库迁移和 Docker 配置。
- 客户端源码中不存在 `fetch`、`wx.request`、API base URL、Token 或重连队列。

### 浏览器验收

- 新档可进入主页并持续增长修为。
- 刷新页面后角色、背包和装备保持一致。
- 后台超过 60 秒再返回时出现离线收益汇总。
- 突破、改名、扩包、物品使用、收取、分解、装备、强化、升星、洞府升级和历练通关后刷新不回退。
- 本地存储不可用时出现明确提示，当前会话仍能操作。
- 重置进度需要二次确认，完成后回到全新 Lv.1 角色。

### 微信验收

- 刘海屏、圆角屏和胶囊按钮区域无遮挡。
- 切前后台只结算一次，不重复发放收益。
- 杀进程后重新进入可以恢复存档。
- 存储配额和写入失败提示符合预期。
- Release 包不包含开发调试面板。

## 8. 未来重新引入后端

需要云存档、跨设备同步、排行榜、防作弊或商业化时再增加后端。推荐顺序：

1. 保持 `shared` 领域规则为唯一数值来源。
2. 为 `LocalGameService` 抽象一个 `GamePersistence` 接口。
3. 先实现可选云备份，不立即把所有操作改成网络强依赖。
4. 明确冲突策略、账号迁移、存档版本和失败回滚。
5. 排行榜、支付和可交易资产必须改为服务端权威。
6. 在现有本地测试基线之上补充集成和端到端测试，不复用本阶段已删除的旧服务端测试。

在这些需求出现之前，当前版本应保持无网络依赖，避免为了可能的未来需求重新引入空置服务端。
